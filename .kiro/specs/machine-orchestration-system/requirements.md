# Requirements Document

## Introduction

本文档定义工业自动化机器编排系统（Machine Orchestration System）的功能需求。该系统允许用户通过图形界面编排工业机器，从基础零件组合成复合组件、模组，最终形成完整的自动化机器。系统支持多种控制板、传感器集成，并提供 DSL 用于自动化逻辑编排。系统设计遵循 Haskell 函数式编程哲学，强调类型安全、纯函数式设计和副作用隔离。

## Glossary

- **System**: 机器编排系统（Machine Orchestration System）
- **Part**: 基础零件，系统提供的最小可组合单元（如电机、气缸、夹爪等）。在统一递归组合模型中，Part 是可组合实体的基础形式
- **Part_Category**: 零件分类，将基础零件库组织为四大类型的分类系统
- **Motor_Type**: 电机类型，零件分类的一种，包含所有电机形态（丝杆滑块、旋转座等），在逻辑层面都是电机抽象
- **Output_Type**: 输出类型，零件分类的一种，包含指示灯、气缸、夹爪、吸气装置等输出设备
- **Input_Type**: 输入类型，零件分类的一种，包含传感器类型的零件，用于采集数据的设备
- **Static_Type**: 静态类型，零件分类的一种，包含不能动的零件（如轴等结构性零件）
- **Component**: 复合组件，由多个零件通过坐标组合而成。在统一递归组合模型中，Component 与 Part、Module、Machine 本质相同，都是可组合实体
- **Module**: 模组，由多个组件组合而成的功能单元。在统一递归组合模型中，Module 与 Part、Component、Machine 本质相同，都是可组合实体
- **Machine**: 完整机器，由多个模组组合而成的自动化设备。在统一递归组合模型中，Machine 与 Part、Component、Module 本质相同，都是可组合实体
- **Composable_Entity**: 可组合实体，Part、Component、Module、Machine 的统一抽象，支持递归组合
- **Motor**: 电机，一种具有多种物理形态的零件（丝杆滑块、旋转座等），在逻辑层面是统一的抽象
- **Actuator**: 执行器，气缸、夹爪、吸气装置的统一抽象，具有输出点和可选的状态传感器输入点。传感器配置是可选的，不同的执行器实例可以有不同的传感器配置（例如：气缸可以有伸出和缩回传感器、仅伸出传感器、或无传感器）
- **State_Sensor**: 状态传感器，用于检测执行器（如气缸）的状态位置的输入传感器。例如：气缸的伸出传感器检测气缸是否已伸出到位，缩回传感器检测气缸是否已缩回到位
- **Action**: 零件的动作状态（如吸气/常规、移动/旋转、闭合/松开等）
- **Sensor**: 传感器，用于采集物理数据的设备（压力传感器、千分表、扫码器等）
- **Control_Board**: 控制板，用于控制机器运行的硬件（雷赛、正运动、模拟等）
- **DSL**: 领域特定语言，用于编排机器自动化运作的脚本语言
- **Automation_Logic**: 自动化逻辑，使用 DSL 编写的机器运行流程
- **Configuration**: 配置，零件、传感器、控制板的参数设置
- **Coordinate**: 坐标，零件在三维空间中的位置和姿态，包括平移和旋转分量
- **Transformation**: 变换，对零件或组件进行的空间操作，包括平移、旋转、缩放等
- **Transformation_Matrix**: 变换矩阵，用于表示和计算坐标变换的数学结构，支持组合和递归应用
- **User_Interface**: 用户界面，用于编排机器和配置参数的图形界面
- **Runtime_Visualization**: 运行时可视化，在界面上显示机器运行动作的功能，支持虚拟设备和真实设备
- **Pure_Function**: 纯函数，无副作用的函数，输出仅依赖输入
- **Effect_Boundary**: 副作用边界，隔离纯净代码和包含副作用的代码的边界
- **Algebraic_Data_Type**: 代数数据类型，使用 Sum Type 和 Product Type 构建的类型系统

## Requirements

### Requirement 1: 零件库管理

**用户故事：** 作为系统用户，我希望系统提供基础零件库，以便我可以选择零件进行机器编排。

#### 验收标准

1. 系统应当提供基础零件库，包括电机、气缸、夹爪、吸气装置和轴
2. 当用户请求零件库时，系统应当返回所有可用零件及其类型定义
3. 系统应当使用代数数据类型（Algebraic_Data_Type）表示每个零件以确保类型安全
4. 系统应当将零件属性定义为纯函数（Pure_Function）转换
5. 系统应当将电机表示为统一的抽象模型，支持多种物理形态（带滑块的丝杆、旋转座等）
6. 系统应当将气缸、夹爪、吸气装置抽象为统一的执行器（Actuator）模型，包含输出点和可选的状态传感器（State_Sensor）输入点
7. 系统应当使用代数数据类型（Algebraic_Data_Type）的 Option/Maybe 类型表示执行器（Actuator）的可选状态传感器（State_Sensor）配置
8. 对于气缸类型的执行器（Actuator），系统应当支持三种传感器配置：无传感器、仅伸出传感器、伸出和缩回传感器
9. 系统应当使用代数数据类型（Algebraic_Data_Type）的和类型（Sum Type）表示不同的传感器配置组合
10. 当电机以丝杆形态存在时，系统应当将滑块的运动作为电机动作的表达
11. 系统应当在逻辑层面将不同物理形态的电机视为同一抽象类型
12. 系统应当将零件库组织为四大类型：电机类型（Motor_Type）、输出类型（Output_Type）、输入类型（Input_Type）、静态类型（Static_Type）
13. 系统应当使用代数数据类型（Algebraic_Data_Type）的和类型（Sum Type）表示零件分类（Part_Category）
14. 当用户浏览零件库时，系统应当按分类（Part_Category）展示零件
15. 系统应当允许用户按分类（Part_Category）筛选零件
16. 电机类型（Motor_Type）应当包含所有电机形态（丝杆滑块、旋转座等）
17. 输出类型（Output_Type）应当包含指示灯、气缸、夹爪、吸气装置等输出设备
18. 输入类型（Input_Type）应当包含各种传感器零件
19. 静态类型（Static_Type）应当包含轴等不可动零件
20. 系统应当确保零件分类系统与统一递归组合模型（Composable_Entity）兼容

### Requirement 2: 零件物理组合

**用户故事：** 作为系统用户，我希望通过坐标系统组合零件，以便形成复合组件。

#### 验收标准

1. 系统应当为每个零件记录其坐标（Coordinate），包括位置和姿态
2. 当用户将零件添加到组件时，系统应当记录零件相对于父组件的相对坐标（Coordinate）
3. 系统应当使用变换矩阵（Transformation_Matrix）表示零件的空间变换
4. 系统应当将坐标（Coordinate）和变换矩阵（Transformation_Matrix）表示为不可变数据结构
5. 当组件进行变换（Transformation）时，系统应当使用纯函数（Pure_Function）动态计算所有子零件的新坐标
6. 系统应当保持子零件相对于父零件的相对坐标（Coordinate）不变
7. 系统应当支持任意数量的零件组合到一个组件中
8. 当零件组合成组件后，系统应当将组件视为单一整体进行移动和旋转变换
9. 系统应当将组件的变换操作应用于所有组成零件，保持它们的相对空间关系不变
10. 系统应当使用纯函数（Pure_Function）通过变换矩阵（Transformation_Matrix）计算组件整体变换后各零件的新位置

### Requirement 3: 统一递归组合模型

**用户故事：** 作为系统用户，我希望将零件、组件、模组和机器视为统一的可组合实体，以便灵活构建任意复杂度的自动化设备。

#### 验收标准

1. 系统应当将零件（Part）、组件（Component）、模组（Module）和机器（Machine）表示为同一递归代数数据类型（Algebraic_Data_Type）
2. 当用户组合任意两个可组合实体时，系统应当创建新的组合实体
3. 系统应当支持任意深度的递归组合，不限制层级数量
4. 系统应当使用纯函数（Pure_Function）在任意组合层级验证结构完整性
5. 系统应当将组合操作定义为满足结合律的纯函数，确保组合顺序不影响最终结构
6. 系统应当为统一组合模型提供统一的变换（Transformation）接口，基于坐标（Coordinate）和变换矩阵（Transformation_Matrix）
7. 当对组合实体进行变换时，系统应当递归地将变换应用于所有子实体，使用纯函数（Pure_Function）计算新坐标

### Requirement 4: 零件动作定义

**用户故事：** 作为系统用户，我希望每个零件都有对应的动作状态，以便控制零件行为。

#### 验收标准

1. 系统应当使用和类型（Sum Types）为每种零件类型定义动作（Action）状态
2. 对于吸气装置，系统应当支持动作：吸气（suction）和常规（normal）
3. 对于轴，系统应当支持动作：直线运动（linear_movement）和旋转（rotation）
4. 对于夹爪，系统应当支持动作：闭合（close）和松开（open）
5. 对于气缸，系统应当支持动作：伸出（extend）和收回（retract）
6. 系统应当在副作用边界（Effect_Boundary）内将动作（Action）转换表示为纯函数（Pure_Function）

### Requirement 5: 动作可视化播放

**用户故事：** 作为系统用户，我希望在界面上播放零件动作，以便验证编排的正确性。

#### 验收标准

1. 当用户选择零件并触发动作（Action）时，用户界面（User_Interface）应当显示动作动画
2. 系统应当使用纯函数（Pure_Function）计算动画帧
3. 系统应当在副作用边界（Effect_Boundary）隔离渲染副作用
4. 系统应当支持组件（Components）、模组（Modules）和机器（Machines）的动作序列播放

### Requirement 6: 传感器类型支持

**用户故事：** 作为系统用户，我希望系统支持多种传感器，以便采集不同类型的物理数据。

#### 验收标准

1. 系统应当支持传感器（Sensor）类型，包括压力传感器、千分表和扫码器
2. 系统应当使用代数数据类型（Algebraic_Data_Type）表示每种传感器（Sensor）类型
3. 系统应当在副作用边界（Effect_Boundary）内定义传感器（Sensor）读取操作
4. 当传感器（Sensor）被添加到系统时，系统应当验证其类型定义

### Requirement 7: 传感器连接方式

**用户故事：** 作为系统用户，我希望支持多种传感器连接方式，以便适配不同的硬件配置。

#### 验收标准

1. 系统应当支持串口连接，每个端口连接一个传感器（Sensor）
2. 系统应当支持串口连接，每个端口连接多个传感器（Sensors）
3. 系统应当支持 USB 连接，使用库特定的读写操作
4. 系统应当将连接配置表示为不可变数据结构
5. 系统应当在副作用边界（Effect_Boundary）隔离 I/O 操作

### Requirement 8: DSL 自动化编排

**用户故事：** 作为系统用户，我希望使用 DSL 编排机器的自动化运作，以便定义复杂的自动化流程。

#### 验收标准

1. 系统应当提供用于定义自动化逻辑（Automation_Logic）的 DSL
2. 系统应当使用纯函数（Pure_Function）将 DSL 脚本解析为抽象语法树（Abstract Syntax Tree）
3. 系统应当在解析时验证 DSL 语法和语义
4. 系统应当使用代数数据类型（Algebraic_Data_Type）表示 DSL 表达式
5. 如果 DSL 语法无效，那么系统应当返回包含行号和列号信息的描述性解析错误

### Requirement 9: DSL 解析器与打印器

**用户故事：** 作为开发者，我希望系统提供 DSL 解析器和打印器，以便可靠地处理自动化脚本。

#### 验收标准

1. 当提供有效的 DSL 脚本时，DSL 解析器（DSL_Parser）应当将其解析为抽象语法树（AST）
2. 当提供无效的 DSL 脚本时，DSL 解析器（DSL_Parser）应当返回描述性错误
3. DSL 美化打印器（DSL_Pretty_Printer）应当将抽象语法树（AST）格式化回有效的 DSL 脚本
4. 对于所有有效的抽象语法树（AST），解析然后打印然后再解析应当产生等价的抽象语法树（往返属性 round-trip property）
5. 系统应当将 DSL 解析器（DSL_Parser）和 DSL 美化打印器（DSL_Pretty_Printer）实现为纯函数（Pure_Function）

### Requirement 10: 控制板抽象接口

**用户故事：** 作为系统用户，我希望系统支持多种控制板，以便适配不同的硬件平台。

#### 验收标准

1. 系统应当使用类型类（type classes）或特征（traits）定义抽象的控制板（Control_Board）接口
2. 系统应当支持雷赛（Lei_Sai）控制板实现
3. 系统应当支持正运动（Zheng_Yun_Dong）控制板实现
4. 系统应当支持用于测试的模拟（Simulated）控制板实现
5. 系统应当允许用户通过用户界面（User_Interface）选择控制板（Control_Board）实现
6. 系统应当在副作用边界（Effect_Boundary）隔离控制板（Control_Board）I/O 操作

### Requirement 11: 零件参数配置

**用户故事：** 作为系统用户，我希望通过界面配置基础零件参数，以便适配物理设备或模拟环境。

#### 验收标准

1. 当用户选择零件时，用户界面（User_Interface）应当显示可配置参数
2. 对于电机零件，系统应当支持配置工作速度和回零模式
3. 系统应当支持配置电机接口到控制板（Control_Board）的连接
4. 系统应当支持配置限位传感器分配
5. 系统应当支持配置传感器端口分配
6. 对于输出类型（Output_Type）零件，系统应当允许用户配置可选的状态传感器（State_Sensor）
7. 对于气缸类型的执行器（Actuator），系统应当支持配置伸出传感器和缩回传感器的端口（可选）
8. 系统应当使用代数数据类型（Algebraic_Data_Type）的 Option/Maybe 类型表示可选的传感器端口配置
9. 当用户配置了状态传感器（State_Sensor）时，系统应当验证传感器端口已指定
10. 如果配置了状态传感器（State_Sensor）但未指定端口，那么系统应当返回描述性验证错误
11. 系统应当在应用前使用纯函数（Pure_Function）验证配置（Configuration）参数
12. 如果配置（Configuration）参数无效，那么系统应当返回描述性验证错误

### Requirement 12: 控制板特定参数

**用户故事：** 作为系统用户，我希望不同控制板可以有不同的参数配置，以便适配硬件差异。

#### 验收标准

1. 当选择控制板（Control_Board）时，系统应当提供板特定的配置（Configuration）参数
2. 系统应当根据所选控制板（Control_Board）类型验证配置（Configuration）参数
3. 系统应当使用带有类型级约束的代数数据类型（Algebraic_Data_Type）表示板特定参数
4. 如果参数与所选控制板（Control_Board）不兼容，那么系统应当返回类型错误

### Requirement 13: 运行时可视化

**用户故事：** 作为系统用户，我希望在自动化逻辑运行时界面显示机器运行动作，以便监控执行状态。

#### 验收标准

1. 当自动化逻辑（Automation_Logic）执行时，系统应当使用纯函数（Pure_Function）计算当前机器状态
2. 用户界面（User_Interface）应当显示当前机器状态的运行时可视化（Runtime_Visualization）
3. 系统应当以最低每秒 10 帧的速率更新可视化
4. 系统应当在副作用边界（Effect_Boundary）隔离渲染操作
5. 系统应当维护状态计算（纯净）和可视化（副作用）之间的分离
6. 当自动化逻辑启动后，系统应当在界面上实时显示每个零件的动作状态
7. 系统应当对虚拟设备和真实设备提供统一的可视化接口
8. 当连接到模拟控制板（Simulated Control_Board）时，系统应当显示虚拟设备的实时动作
9. 当连接到真实控制板（Control_Board）时，系统应当根据控制板反馈显示真实设备的实时动作
10. 系统应当使用纯函数（Pure_Function）将设备状态映射到可视化表示，无论设备类型

### Requirement 14: 自动化动作集管理

**用户故事：** 作为系统用户，我希望保存多套自动化动作，以便在不同场景下使用不同的自动化流程。

#### 验收标准

1. 当用户定义自动化逻辑（Automation_Logic）时，系统应当允许使用唯一标识符保存它
2. 系统应当为同一台机器（Machine）存储多个自动化逻辑（Automation_Logic）定义
3. 当用户请求已保存的自动化逻辑（Automation_Logic）时，系统应当通过标识符检索它
4. 系统应当使用纯函数（Pure_Function）序列化和反序列化自动化逻辑（Automation_Logic）
5. 对于所有已保存的自动化逻辑（Automation_Logic），序列化然后反序列化应当产生等价的逻辑（往返属性 round-trip property）

### Requirement 15: 自动化逻辑执行

**用户故事：** 作为系统用户，我希望点击执行特定自动化逻辑后系统能稳定运行，以便完成生产任务。

#### 验收标准

1. 当用户触发自动化逻辑（Automation_Logic）执行时，系统应当解释 DSL 并执行动作
2. 系统应当使用不可变数据结构维护执行状态
3. 系统应当优雅地处理执行错误并返回到安全状态
4. 系统应当记录执行期间的所有状态转换
5. 系统应当在副作用边界（Effect_Boundary）隔离所有控制板（Control_Board）命令
6. 如果执行期间发生错误，那么系统应当停止执行并报告带有上下文的错误

### Requirement 16: 浮高机工件测试流程（未来实现）

**用户故事：** 作为操作员，我希望机器能自动测试工件的浮高特性，以便获取常态高度、受压高度和释放后高度。

**注意：** 此需求作为示例场景，暂不要求实现。但其依赖的基础功能（零件编排、动作系统、传感器、DSL、控制板等）必须完成。

#### 验收标准

1. 当工件放置在测试座上时，机器（Machine）应当测量其常态高度
2. 当施加压力时，机器（Machine）应当测量工件在指定压力下的高度
3. 当释放压力时，机器（Machine）应当测量工件在压力释放后的高度
4. 系统应当记录所有三个高度测量值及其时间戳
5. 系统应当使用不可变数据结构表示测量数据

### Requirement 17: 浮高机料盘自动化（未来实现）

**用户故事：** 作为操作员，我希望机器能自动处理多个料盘，以便实现批量测试。

**注意：** 此需求作为示例场景，暂不要求实现。但其依赖的基础功能（零件编排、动作系统、传感器、DSL、控制板等）必须完成。

#### 验收标准

### Requirement 19: 类型安全保证

5. 系统应当使用新类型模式（newtype patterns）区分语义不同但基础类型相同的值

### Requirement 20: 副作用隔离

**用户故事：** 作为开发者，我希望系统严格隔离纯净代码和副作用代码，以便提高可测试性和可维护性。

#### 验收标准

1. 系统应当将核心业务逻辑实现为纯函数（Pure_Function）
2. 系统应当在副作用边界（Effect_Boundary）隔离所有 I/O 操作
3. 系统应当使用显式类型签名标记副作用函数（例如 IO monad、Effect 类型）
4. 系统应当在代码注释中记录副作用边界（Effect_Boundary）
5. 系统应当以清晰分离的方式构建模块：纯净核心和副作用外壳

### Requirement 21: 函数式组合

### Requirement 28: 输出类型零件的状态反馈

**用户故事：** 作为系统用户，我希望通过可选的状态传感器获取输出类型零件的实时状态，以便实现可靠的自动化逻辑执行。

#### 验收标准

1. 当输出类型（Output_Type）零件配置了状态传感器（State_Sensor）时，系统应当能够读取传感器状态
2. 对于配置了伸出传感器的气缸，当气缸伸出到位时，系统应当检测到伸出传感器信号
3. 对于配置了缩回传感器的气缸，当气缸缩回到位时，系统应当检测到缩回传感器信号
4. 系统应当使用代数数据类型（Algebraic_Data_Type）的 Option/Maybe 类型表示可选的传感器状态读取结果

7. 系统应当使用纯函数（Pure_Function）处理传感器状态数据的转换和验证
8. 当自动化逻辑（Automation_Logic）需要等待执行器（Actuator）到位时，系统应当支持基于状态传感器（State_Sensor）的等待条件
9. 如果配置了状态传感器（State_Sensor）但读取失败，那么系统应当返回描述性错误
10. 系统应当支持在 DSL 中引用状态传感器（State_Sensor）状态，用于条件判断和流程控制

## Notes

本需求文档遵循 EARS 模式和 INCOSE 质量规则，确保每个需求都是可测试、明确和完整的。系统设计强调 Haskell 函数式编程哲学，包括：

- 使用代数数据类型确保类型安全
- 严格隔离纯函数和副作用代码
- 应用范畴论概念（Functor、Applicative、Monad）
- 支持惰性求值和函数组合
- 通过类型系统在编译时捕获错误

所有解析器和序列化器都包含了 round-trip 属性要求，确保数据转换的可靠性。

### 关键架构特性

1. **统一递归组合模型**：Part、Component、Module、Machine 本质上是同一种可组合实体（Composable_Entity），支持任意深度的递归组合，不存在严格的层级限制。

2. **零件多形态抽象**：电机等零件在逻辑层面是统一的抽象，但可以有多种物理形态表达（如丝杆滑块、旋转座）。气缸、夹爪、吸气装置等执行器共享统一的抽象模型（输出点 + 可选限位传感器输入点）。

3. **基于坐标的组合模型**：系统不使用显式的物理连接点，而是通过记录每个零件的坐标（位置和姿态）来表示组合关系。当父零件或组件进行变换时，使用变换矩阵动态计算所有子零件的新坐标。这种设计更简洁、更灵活，支持任意数量的子零件组合，并且更符合函数式编程的数学化思维。

4. **组件整体变换**：当零件组合成组件后，所有移动、旋转等变换操作都作用于整个组件作为一个单元，而不是单独的零件。变换通过纯函数式的坐标变换矩阵计算实现。

5. **统一可视化接口**：运行时可视化对虚拟设备和真实设备提供统一的接口，确保无论连接何种控制板，都能实时显示每个零件的动作状态。

6. **可选传感器配置模型**：输出类型（Output_Type）零件的状态传感器（State_Sensor）配置是可选的，使用 Option/Maybe 类型表示。不同的零件实例可以有不同的传感器配置（例如：气缸可以有伸出和缩回传感器、仅伸出传感器、或无传感器）。这种设计通过代数数据类型确保类型安全，并在编译时验证传感器配置的有效性。状态传感器用于反馈零件的实时状态，对于实现可靠的自动化逻辑执行（如等待气缸伸出到位后再继续）至关重要。

7. **浮高机需求范围**：Requirements 16-18（浮高机相关）标注为未来实现，但其依赖的所有基础功能（零件编排、动作系统、传感器、DSL、控制板等）必须完成。
